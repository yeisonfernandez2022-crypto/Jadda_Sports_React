## MÓDULO 4: Siempre disponible y fácil de mantener (RNF-004)

### Identificación:

| Campo | Valor |
| :--- | :--- |
| **ID** | RNF-004 |
| **Nombre** | Siempre disponible y fácil de mantener |
| **Categoría** | Disponibilidad y Tolerancia a fallos |
| **Prioridad** | Alta |
| **Estado** | Implementado parcialmente |

### Requisitos:

* **RNF-004.1 — Alta disponibilidad del servicio:**
    * El sistema debe garantizar una tasa de disponibilidad mínima del 99.5% del tiempo operativo (`uptime`), excluyendo ventanas de mantenimiento.
* **RNF-004.2 — Integración modular aislada:**
    * La arquitectura debe permitir la adición de nuevos módulos funcionales sin afectar el funcionamiento de los existentes.
* **RNF-004.3 — Mecanismos automatizados de respaldo:**
    * El sistema debe ejecutar copias de seguridad (`backups`) diarias de la base de datos.
* **RNF-004.4 — Recuperación ante desastres (RTO/RPO):**
    * Ante una caída crítica, el sistema debe restablecer sus operaciones centrales y recuperar la consistencia de la información.
* **RNF-004.5 — Arquitectura modular desacoplada:**
    * El código debe estar estructurado bajo un enfoque modular para simplificar el mantenimiento.
* **Nota de implementación:** Parcial.
    * ✅ RNF-004.2/4.5: arquitectura por controladores + rutas + utilidades, totalmente modular.
    * ✅ RNF-004.1 parcial: `setup.js` re-crea tablas y datos al arrancar (recuperación ante pérdida del volumen).
    * ⚠️ RNF-004.3: copias de seguridad **scripteadas y probadas** (`scripts/backup.ps1`, `scripts/respaldar.sh` — mysqldump dentro del contenedor, rotación 7 días; restauración verificada E2E); la **tarea programada** (schtasks) queda por agendar en el servidor real (MC-07).
    * ⚠️ RNF-004.4: RPO/RTO definidos en `docs/entregables/entregable-s02-planes.md` (RPO 24 h, RTO 1 h, restauración medida); el monitoreo de uptime externo sigue pendiente (existe sonda `/health` con healthcheck de contenedor).
