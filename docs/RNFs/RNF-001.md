## MÓDULO 1: SEGURIDAD DE LA INFORMACIÓN (RNF-001)

### Identificación:

| Campo | Valor |
| :--- | :--- |
| **ID** | RNF-001 |
| **Nombre** | Seguridad |
| **Categoría** | Seguridad de la información |
| **Prioridad** | Crítica |
| **Estado** | Implementado |

### Requisitos:

* **RNF-001.1 — Hashing de contraseñas:**
    * Las contraseñas de los usuarios deben almacenarse mediante hashing con el algoritmo **bcrypt**. Nunca se almacenan en texto plano ni se incluyen en respuestas de la API.
* **RNF-001.2 — Tokens JWT:**
    * La autenticación debe basarse en tokens JWT (JSON Web Tokens) firmados con algoritmo **HS256**:
    * **Access token:** duración de 15 minutos.
    * **Refresh token:** duración de 7 días.
    * La clave secreta debe tener mínimo 32 caracteres y almacenarse en variable de entorno.
* **RNF-001.3 — Prevención de enumeración de usuarios:**
    * Los mensajes de error en endpoints de autenticación deben ser genéricos:
    * En login: "Incorrect email or password" (sin distinguir si el email existe).
    * En forgot-password: siempre retornar el mismo mensaje, sin revelar si el email está registrado.
* **RNF-001.4 — Validación de entradas:**
    * Todas las entradas del usuario deben validarse tanto en el frontend como en el backend:
    * **Frontend:** validación con lógica React antes de enviar.
    * **Backend:** validación con Pydantic (schemas tipados y restrictivos).
* **RNF-001.5 — Protección contra inyección SQL:**
    * El sistema debe usar SQLAlchemy ORM para todas las consultas a la base de datos. No se permite SQL crudo sin parametrizar.
* **RNF-001.6 — CORS (Cross-Origin Resource Sharing):**
    * En desarrollo: permitir únicamente `http://localhost:5173`.
    * En producción: configurar orígenes específicos; nunca usar `allow_origins=["*"]`.
* **RNF-001.7 — Variables de entorno:**
    * Toda información sensible (claves secretas, credenciales de BD, configuraciones SMTP) debe almacenarse en archivos `.env` no versionados. Se debe proveer un `.env.example` como plantilla.
* **RNF-001.8 — Fortaleza de contraseñas:**
    * Las contraseñas deben cumplir requisitos mínimos:
    * Mínimo 8 caracteres.
    * Al menos 1 letra mayúscula.
    * Al menos 1 letra minúscula.
    * Al menos 1 número.

## MÓDULO 2: SEGURIDAD EN COMUNICACIONES Y DATOS (RNF-002)

### Identificación:

| Campo | Valor |
| :--- | :--- |
| **ID** | RNF-002 |
| **Nombre** | Cifrado y Cumplimiento |
| **Categoría** | Seguridad y Privacidad |
| **Prioridad** | Crítica |
| **Estado** | Por implementar |

### Requisitos:

* **RNF-002.1 — Protocolo HTTPS seguro:**
    * El sistema debe utilizar de manera obligatoria el protocolo HTTPS para todas las comunicaciones entre cliente y servidor, denegando conexiones HTTP inseguras mediante redirecciones forzadas TLS 1.3.
* **RNF-002.2 — Mitigación de vulnerabilidades OWASP (Fuerza bruta, CSRF, XSS):**
    * El sistema debe implementar mecanismos de seguridad avanzados:
    * **Fuerza bruta:** Bloqueo temporal de IP/cuenta tras 5 intentos fallidos de login.
    * **XSS:** Sanitización exhaustiva de entradas HTML y configuración de cabeceras de seguridad.
    * **CSRF:** Validación estricta de tokens antifalsificación en peticiones de mutación de datos.
* **RNF-002.3 — Sesiones con expiración automática:**
    * El sistema debe gestionar sesiones seguras que expiren automáticamente tras un periodo definido de 30 minutos de inactividad del usuario, invalidando los tokens correspondientes.
* **RNF-002.4 — Almacenamiento de datos sensibles cifrados:**
    * Los datos sensibles persistidos en el almacenamiento secundario, tales como tokens de pasarelas de pago o identificaciones fiscales, deben estar protegidos mediante cifrado en reposo AES-256.
* **RNF-002.5 — Cumplimiento normativo legal:**
    * El sistema debe ajustarse estrictamente a las normativas de protección de datos vigentes (como la Ley de Protección de Datos Personales / GDPR aplicable), garantizando los derechos de acceso, rectificación y supresión de datos a petición del usuario.

## MÓDULO 3: EFICIENCIA, DESEMPEÑO Y ESCALABILIDAD (RNF-003)

### Identificación:

| Campo | Valor |
| :--- | :--- |
| **ID** | RNF-003 |
| **Nombre** | Rendimiento y Escalabilidad |
| **Categoría** | Eficiencia y Desempeño |
| **Prioridad** | Alta |
| **Estado** | Por implementar |

### Requisitos:

* **RNF-003.1 — Tiempo máximo de respuesta general:**
    * El sistema debe responder a las solicitudes generales de la API en un tiempo máximo de 2 segundos bajo condiciones de carga normal.
* **RNF-003.2 — Carga óptima del catálogo de productos:**
    * La consulta y renderizado del catálogo principal de productos deportivos no debe exceder un tiempo máximo de 3 segundos utilizando paginación e índices optimizados.
* **RNF-003.3 — Procesamiento de operaciones críticas:**
    * El sistema debe completar operaciones críticas de negocio (tales como la confirmación de pago o el procesamiento del checkout) en un tiempo máximo de 5 segundos.
* **RNF-003.4 — Concurrencia masiva sin degradación:**
    * El backend debe ser capaz de soportar múltiples usuarios concurrentes interactuando en simultáneo en la plataforma sin que se experimente una degradación significativa del rendimiento global.
* **RNF-003.5 — Escalabilidad horizontal de infraestructura:**
    * La arquitectura y el despliegue del sistema deben permitir la escalabilidad horizontal mediante contenedores y balanceadores de carga para mitigar eficientemente incrementos abruptos en la demanda comercial.
* **RNF-003.6 — Optimización de almacenamiento histórico de compras:**
    * La base de datos relacional debe configurarse para estructurar y almacenar de manera eficiente los registros históricos de compras masivas, previniendo cuellos de botella mediante particionamiento lógico si fuera necesario.
* **RNF-003.7 — Soporte para catálogos volumétricos:**
    * El sistema debe mantener estables sus métricas de rendimiento y velocidad de respuesta aun cuando la base de datos de productos crezca a un alto volumen de ítems SKU.

## MÓDULO 4: DISPONIBILIDAD, MANTENIMIENTO Y TOLERANCIA A FALLOS (RNF-004)

### Identificación:

| Campo | Valor |
| :--- | :--- |
| **ID** | RNF-004 |
| **Nombre** | Resiliencia y Mantenibilidad |
| **Categoría** | Disponibilidad y Tolerancia a fallos |
| **Prioridad** | Alta |
| **Estado** | Por implementar |

### Requisitos:

* **RNF-004.1 — Alta disponibilidad del servicio:**
    * El sistema debe garantizar una tasa de disponibilidad mínima del 99.5% del tiempo operativo del negocio (`uptime`), excluyendo ventanas de mantenimiento previamente notificadas.
* **RNF-004.2 — Integración modular aislada:**
    * La arquitectura debe permitir la adición e integración de nuevos módulos funcionales o extensiones de código de forma aislada, sin perjudicar el correcto funcionamiento de los servicios existentes.
* **RNF-004.3 — Mecanismos automatizados de respaldo:**
    * El sistema debe ejecutar políticas automatizadas de copias de seguridad (`backups`) diarias de la base de datos y de los archivos de configuración en servidores de almacenamiento redundantes e independientes.
* **RNF-004.4 — Recuperación ante desastres y fallos (RTO/RPO):**
    * Ante una caída crítica de la infraestructura, el sistema debe restablecer sus operaciones centrales y recuperar la consistencia de la información en un lapso máximo de tiempo definido en el plan de contingencia técnico.
* **RNF-004.5 — Despliegues y actualizaciones sin downtime:**
    * El pipeline de CI/CD debe facilitar la publicación de actualizaciones de software de forma continua y transparente, sin afectar en absoluto la disponibilidad en vivo del servicio para el usuario final.
* **RNF-004.6 — Arquitectura modular desacoplada:**
    * El código fuente debe estar estructurado bajo las buenas prácticas de desarrollo y un enfoque de arquitectura modular o de microservicios para simplificar las labores de mantenimiento predictivo, preventivo y correctivo.

## MÓDULO 5: USABILIDAD, ACCESIBILIDAD Y EXPERIENCIA DE USUARIO (RNF-005)

### Identificación:

| Campo | Valor |
| :--- | :--- |
| **ID** | RNF-005 |
| **Nombre** | Usabilidad y Accesibilidad |
| **Categoría** | Experiencia de usuario (UX) |
| **Prioridad** | Media |
| **Estado** | Por implementar |

### Requisitos:

* **RNF-005.1 — Interfaz de usuario intuitiva:**
    * El diseño de la interfaz gráfica debe ser limpio, intuitivo y estandarizado, asegurando que un comprador promedio navegue y entienda las mecánicas de la tienda sin necesidad de asistencia o tutoriales.
* **RNF-005.2 — Diseño responsivo multi-dispositivo:**
    * El frontend del sitio web debe ser 100% accesible y auto-adaptable en pantallas de dispositivos móviles, tabletas y computadoras de escritorio.
* **RNF-005.3 — Estándares básicos de accesibilidad:**
    * El desarrollo de las interfaces debe cumplir con las pautas y estándares básicos de accesibilidad web (como WCAG), incluyendo contrastes de color adecuados y compatibilidad con lectores de pantalla.
* **RNF-005.4 — Checkout ágil limitado (Regla de los 5 pasos):**
    * El flujo completo del proceso de compra desde el carrito hasta la pantalla de confirmación exitosa debe poder consolidarse en un máximo de 5 pasos consecutivos.
* **RNF-005.5 — Compatibilidad multiplataforma de navegadores:**
    * La aplicación web debe asegurar su correcto despliegue estético y funcional en las últimas versiones estables de los principales navegadores comerciales del mercado (Google Chrome, Mozilla Firefox, Safari, Microsoft Edge).
* **RNF-005.6 — Compatibilidad con sistemas operativos modernos:**
    * La solución debe interactuar fluidamente con las API y vistas Webview de sistemas operativos de escritorio y móviles vigentes (Windows, macOS, Android, iOS).

## MÓDULO 6: INTEGRACIÓN, AUDITORÍA Y COMPORTAMIENTO ASÍNCRONO (RNF-006)

### Identificación:

| Campo | Valor |
| :--- | :--- |
| **ID** | RNF-006 |
| **Nombre** | Integración y Operaciones |
| **Categoría** | Comunicaciones y Auditoría |
| **Prioridad** | Alta |
| **Estado** | Por implementar |

### Requisitos:

* **RNF-006.1 — Comunicación basada en APIs REST:**
    * Todos los servicios internos y el traspaso de información con los clientes web/móviles deben usar estándares de comunicación síncronos bajo el patrón arquitectónico REST utilizando payloads formateados en JSON.
* **RNF-006.2 — Integración fluida con servicios externos:**
    * El backend debe contar con pasarelas de conexión robustas para integrarse ágilmente con proveedores y APIs de terceros (ej. pasarelas de pago, servicios postales logísticos o proveedores de OAuth).
* **RNF-006.3 — Consistencia transaccional ACID:**
    * El sistema debe garantizar estrictamente la consistencia y la atomicidad de los datos en todas las operaciones financieras o de inventario, asegurando que ante una interrupción física no se pierda información en los procesos críticos del negocio.
* **RNF-006.4 — Registro de logs operativos:**
    * El backend debe escribir de forma permanente archivos de bitácora (`logs`) detallados que registren las operaciones importantes de los servicios técnicos para facilitar el rastreo de errores.
* **RNF-006.5 — Trazabilidad y auditoría de administración:**
    * El sistema debe auditar y dejar constancia histórica de las acciones y modificaciones críticas ejecutadas tanto por usuarios regulares como por administradores del backoffice (ej. cambios de precios, modificaciones de stock).
* **RNF-006.6 — Monitoreo en tiempo real:**
    * La infraestructura del servidor de base de datos y de la API debe estar conectada a herramientas de telemetría y monitoreo en tiempo real para evaluar el consumo de memoria, CPU y concurrencia.
* **RNF-006.7 — Alertas ante eventos críticos:**
    * El sistema debe despachar alertas automáticas e inmediatas al equipo de ingeniería (vía Slack, correo o Webhooks) al detectar excepciones imprevistas o eventos críticos de infraestructura.
* **RNF-006.8 — Velocidad en el despacho de notificaciones:**
    * Las notificaciones automáticas originadas por cambios de estado en los pedidos deben enviarse por correo electrónico al cliente en un tiempo menor a 1 minuto desde que ocurre el evento en el sistema.
* **RNF-006.9 — Mecanismo de reintento para correos fallidos:**
    * El microservicio o worker encargado de las notificaciones por correo electrónico debe poseer un sistema de colas automatizado para reintentar el envío de un mensaje en caso de detectar caídas temporales en la comunicación con el servidor SMTP.
