### RF-018 — Seleccionar el método de pago
* **Identificación:**

| Campo | Valor |
| :--- | :--- |
| **ID** | RF-018 |
| **Nombre** | Seleccionar el método de pago |
| **Módulo** | Checkout / Pasarela de pagos |
| **Prioridad** | Alta |
| **Estado** | Implementado |
| **Fecha** | Mayo 2026 · ampliado con Wompi (24 oct 2026) |

* **Descripción:** Permite al comprador elegir cómo pagará durante el checkout y, con la pasarela activa, culminar el pago con Wompi (Tarjeta, PSE, Nequi, Daviplata y Bancolombia). El frontend muestra los métodos aceptados como chips informativos (`GET /api/pagos/config` entrega los métodos reales del sandbox) y los datos específicos de pago (número de tarjeta, token PSE, código Nequi…) ya NO se piden en el sitio: se eligen y digitan dentro del widget seguro de Wompi.
* **Entradas:**

| Campo | Tipo | Obligatorio | Validaciones |
| :--- | :--- | :--- | :--- |
| `metodoPago` | Texto | No* | Valores: `"tarjeta"`, `"pse"`, `"nequi"`, `"daviplata"`, `"bancolombia"`; con pasarela activa se ignora en el checkout y solo orienta la UI |
| (sin entrada) | — | — | *Con `PAYMENT_GATEWAY=wompi` el checkout pide CERO datos de pago: dirección + datos de envío bastan |

* **Proceso:**
    1. El comprador escoge su opción preferida (o simplemente usa el método sugerido cuando hay pasarela) y completa el checkout.
    2. El backend crea la venta en `PENDIENTE_PAGO` y recalcula todos los totales en el servidor (nunca confía al cliente).
    3. Con pasarela activa: `POST /api/pagos/pagar` genera la referencia `JADDA-<idVenta>-<rand8>`, firma `integrity` (SHA256) y devuelve la URL del widget; el frontend redirige a Wompi.
    4. Wompi procesa el pago (Tarjeta/PSE/Nequi/Daviplata/Bancolombia); la confirmación llega por pull (`GET /api/pagos/estado/:idVenta`, sondeo cada 3,5 s desde la página de éxito) o webhook firmado (`/api/pagos/webhook`).
    5. APPROVED → venta `CONFIRMADA` + correo con factura + avisos a comprador/admin (y vendedor si su producto); DECLINED/VOIDED → `CANCELADA` + reingreso de stock (y 48 h sin pago → expiración automática).
    6. Sin pasarela (vacío `PAYMENT_GATEWAY`): el flujo clásico guarda `DATOS_PAGO` del formulario y la venta queda `COMPLETADA` directo.
* **Salidas:**

| Escenario | Código HTTP | Respuesta |
| :--- | :--- | :--- |
| Sesión de pago creada (pasarela) | 200 | `{ ok, urlCheckout, referencia }` → redirect al widget |
| Venta clásica sin pasarela | 201 | Redirección a página de confirmación |
| Pull de estado | 200 | `{ ok, estadoVenta: PENDIENTE_PAGO \| CONFIRMADA \| CANCELADA }` |
| Venta de otro usuario / ya pagada | 400/404/409 | Mensaje de error; `pagar` es idempotente (misma URL si se repite en `PENDIENTE_PAGO`) |

* **Endpoints asociados:**

| Método | Ruta | Auth requerida | Descripción |
| :--- | :--- | :--- | :--- |
| POST | `/api/checkout/procesar` | Sí | Crea la venta (transacción con `FOR UPDATE` + guard 409 de stock) |
| GET | `/api/pagos/config` | No (público) | `{ activo, ambiente, metodos[] }` según el sandbox de Wompi |
| POST | `/api/pagos/pagar` | Sí (dueño de la venta, rate 8/5 min) | Crea o re-usa la sesión de pago de Wompi y su URL firmada |
| GET | `/api/pagos/estado/:idVenta` | Sí (dueño + rate 90/min) | Sondeo del estado del pago (pull) |
| POST | `/api/pagos/webhook` | Firma HMAC (sin sesión, rate 60/min) | Eventos de Wompi: checksum SHA256 + idempotencia en `PAGOS_EVENTOS` + re-consulta de la transacción vía API antes de confirmar |
| GET | `/api/usuarios/metodos-pago` | Sí | Lista de métodos de pago guardados del usuario (perfil) |
