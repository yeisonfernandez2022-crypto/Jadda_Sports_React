### RF-023 — Cancelar un pedido antes de su envío
* **Identificación:**

| Campo | Valor |
| :--- | :--- |
| **ID** | RF-023 |
| **Nombre** | Cancelar un pedido antes de su envío |
| **Módulo** | Pedidos |
| **Prioridad** | Media |
| **Estado** | Implementado |
| **Fecha** | Mayo 2026 (actualizado 2026-10-27) |

* **Descripción:** Permite anular un pedido antes del despacho. El cliente lo hace desde Mis compras; el administrador y el vendedor también pueden cancelar una venta desde sus paneles. El backend marca la venta como `CANCELADA` con `CANCELADA_POR` (`CLIENTE`, `TIENDA` o `SISTEMA`), reingresa el stock cuando la cancelación es del cliente y, si el pago estaba confirmado y el pedido no había salido, aprueba **automáticamente** en `DEVOLUCIONES` el reembolso **de los productos y del costo de envío**, sin revisión del administrador. Si no se registró ningún cobro, no se crea reembolso. El reembolso es un registro en base de datos: la devolución del dinero real se procesa en el panel del proveedor de pagos.
* **Entradas:**

| Campo | Tipo | Obligatorio | Validaciones |
| :--- | :--- | :--- | :--- |
| `order_id` | Entero (Path) | Sí | ID del pedido que se pretende cancelar |

* **Proceso:**
    1. El cliente solicita la anulación desde Mis compras (`POST /api/compras/:id/cancelar`); el admin o el vendedor la ejecutan cambiando el estado a `CANCELADA` (`PUT /api/admin/compras/:id/estado` o `PUT /api/vendedor/ventas/:id/estado`).
    2. La cancelación del cliente solo procede si la venta está en `COMPLETADA`, `CONFIRMADA`, `PENDIENTE` o `PENDIENTE_PAGO` y el envío no figura como `EN_CAMINO`/`ENTREGADO`. El cliente puede cancelar compras que incluyan productos de vendedores; el vendedor y el administrador también pueden hacerlo desde sus paneles.
    3. **Cancelación del cliente, dentro de una transacción:** devuelve el stock de cada variante comprada (`PRODUCTO_VARIANTES.STOCK + CANTIDAD`), registra `ENTRADA` en `MOVIMIENTOS_STOCK`, marca `ESTADO = CANCELADA`, `CANCELADA_POR = 'CLIENTE'` y `ESTADO_ENVIO = CANCELADO`; el rollback revierte todo si algo falla.
    4. **Cancelación por admin/vendedor:** usa el helper `cancelarVentaYReembolsar` con `CANCELADA_POR = 'TIENDA'`; no modifica stock ni el estado del envío (alcance deliberado), pero sí evalúa el pago y el despacho para el reembolso.
    5. **Reembolso automático:** si `ventaPagada(ESTADO, DATOS_PAGO)` es verdadero y el envío no salió, agrega las líneas por `ID_PRODUCTO`, crea o actualiza las `DEVOLUCIONES` con `TIPO = 'REEMBOLSO'`, `ESTADO = 'APROBADA'`, `FECHA_PROCESADA = NOW()` y motivo `"Reembolso por cancelación del pedido"`. El total usa `DETALLE_VENTAS.SUBTOTAL` **más `ENVIOS.COSTO_ENVIO`** (solo si el pedido no había sido despachado; si el envío ya salió, se reembolsan solo los productos). Si ya existía un reembolso aprobado no se duplica. Si la venta no tenía cobro confirmado (`PENDIENTE_PAGO` o pago declinado), no se crea reembolso.
    6. Tras el commit se notifica al cliente por campana/correo (`notificarCambioEstado`) y, cuando hay reembolso, con la ruta `/perfil/reembolso/:idVenta`.
* **Salidas:**

| Escenario | Código HTTP | Respuesta |
| :--- | :--- | :--- |
| Cancelación del cliente aceptada | 200 | `{ok, msg: "Compra cancelada", reembolso}` (el objeto `reembolso` incluye `automatico: true`, `totalProductos`, `costoEnvio`, `total`, `filas` o `null`) |
| Cancelación por admin/vendedor | 200 | `{ok, msg, pagoConfirmado, reembolso}` con mensaje de reembolso aprobado o `"Estado actualizado"` |
| Cancelación repetida (admin/vendedor) | 200 | `{ok: true, encontrada: true, sinCambios: true}` sin duplicar el reembolso |
| Compra ya cancelada (cliente) | 400 | Mensaje: `"Esta compra ya fue cancelada"` |
| Pedido no cancelable | 400 | Mensaje: `"Esta compra ya no se puede cancelar"` |
| Envío ya salió del almacén (cliente) | 400 | Mensaje: `"El pedido ya salió del almacén y no puede cancelarse"` |
| Pedido inexistente / ajeno | 404 / 403 | Compra no encontrada / la venta no incluye productos del vendedor |

* **Endpoints asociados:**

| Método | Ruta | Auth requerida | Descripción |
| :--- | :--- | :--- | :--- |
| POST | `/api/compras/:id/cancelar` | Cliente | Cancela su compra, libera stock y aprueba el reembolso automático de productos + envío si corresponde |
| PUT | `/api/admin/compras/:id/estado` | Admin | Cambia el estado de la venta; `CANCELADA` aplica reembolso automático de productos + envío |
| PUT | `/api/vendedor/ventas/:id/estado` | Vendedor | Cambia el estado de una venta con productos propios; `CANCELADA` aplica el mismo reembolso |

* **Reglas de negocio:**
    * **RN-010:** El cliente no puede cancelar un pedido cuyo estado logístico figure como enviado (`EN_CAMINO`, `ENTREGADO`); el backend lo valida contra `ENVIOS.ESTADO_ENVIO`. Admin/vendedor pueden marcar `CANCELADA` una venta despachada, pero en ese caso **no** se genera reembolso automático.
    * **Reembolso:** automático y aprobado en `DEVOLUCIONES` para pagos confirmados antes del despacho; no requiere revisión del admin. Cubre el valor de los productos **y el costo de envío**; si la venta ya estaba despachada solo se reembolsan los productos (o nada si el admin/vendedor la cancela después del envío). No hay pasarela de pagos real, por lo que el dinero se devuelve desde el panel del proveedor.
    * **Atribución:** `CANCELADA_POR` distingue `CLIENTE`, `TIENDA` (admin/vendedor) y `SISTEMA` (expiración de pago); la UI muestra "Cancelada por ti", "Cancelada por la tienda" o "Pago no completado".
    * **Stock:** la cancelación del cliente libera el stock de las variantes compradas y lo registra en `MOVIMIENTOS_STOCK`; las cancelaciones de admin/vendedor no lo modifican (decisión operativa). Las ventas creadas antes del 2026-08-13 nunca decrementaron stock en checkout, por lo que su cancelación puede reingresar unidades que no se habían descontado.
